# Firmware library

Phase 4 imports passive local files. It does not obtain firmware from a router, unpack or execute files, or establish compatibility/authenticity.

Open **Firmware library → Import Firmware**. A Windows Open dialog selects one file. Rust keeps an open read-only sharing lease and returns a random selection ticket, filename, byte count, expiry and configured limit. Review the details, optionally add a description, then **Confirm import**. Cancelling the selection releases its lease. Tickets expire after five minutes, are single-use and are limited to eight pending selections. JavaScript cannot submit a filesystem path for import or export.

The import creates a persistent job before copying. Progress shows the actual stage and byte count; hashing stages start their own progress counts. The library displays only committed artifacts, with original filename, size, SHA-256, import count, date, format and current integrity/storage status. File extensions never establish firmware format: this phase conservatively records `UNKNOWN`. Imported files are always `user_import` with unverified provenance. Vendor/acquisition/build categories are reserved for workflows with evidence.

Search uses filenames and digest substrings with literal matching, plus integrity, source and UTC import-date filters. Results are paginated in groups of 25. SQLite handles filtering/counts; React does not load an unbounded collection. Artifact details show the latest 50 import occurrences and integrity checks, while retaining full history in SQLite. Jobs and activity show the latest 100 records.

**Verify Integrity** creates a real background verification job. It streams the stored blob, compares SHA-256 and size, saves the result/history and records activity. A mismatch, missing blob or unreadable blob is reported explicitly; no corrupted content is replaced. A matching checksum describes stored bytes only, never firmware safety or device support. Startup checks availability/size and withdraws last session's `verified` label to `not_checked`; a fresh full verification is needed for a current verified label.

**Export Manifest** opens the Windows Save dialog and writes a new JSON file without overwriting an existing file. Manifest schema 1 includes the hash, size, format, integrity state/time and latest 50 filename/provenance occurrences, with total and omitted counts. It excludes absolute paths, descriptions, device IDs and credentials. Export is bounded metadata work on a blocking worker, rather than a queued binary-processing job. Publication is the save commit point: IPC returns `saved`, `activityRecorded` and `warning` separately. If the subsequent audit transaction fails, the valid saved file remains and the UI reports that it was saved with an activity warning. The audit event and activity link commit together. Cancellation reports `saved=false`; a publication error still fails without overwriting an existing file. The manifest is unsigned and does not prove authenticity or flashing support.

Defaults: 1 MiB buffers; one binary-processing worker; at most 16 active/queued jobs; 2 GiB maximum source size. Set process environment `OBTAINER_IMPORT_MAX_BYTES` to an integer from 1 byte through 8 GiB before launching to change that limit. The selection preview displays it. Sources must be regular local files; UNC/device/alternate-stream paths, mapped network drives and reparse-point directories/files are rejected conservatively. Files managed through cloud reparse points should first be copied to a normal local folder. Storage must support same-volume hard links.

All existing application data remains at `%LOCALAPPDATA%\OBTAINER\`. Schema 4 complements the existing artifact/job tables with metadata/history tables. No original device/settings/profile record is removed. See [vault guarantees](FIRMWARE_VAULT.md), [persistent jobs](JOB_ENGINE.md), and [verification evidence](PHASE_4_VERIFICATION.md).

Automated native tests use a separate, explicitly enabled executable and a unique marked run beneath the Windows LocalAppData known folder's `OBTAINER-NativeTests` directory. Its database, vault, logs, workspaces, reports and WebView data are isolated. Harmless generated fixtures are used for corruption/interruption tests. Ordinary launches retain the path above. See [native test activation and cleanup](NATIVE_TESTING.md) and [Phase 4.1 verification](PHASE_4_1_VERIFICATION.md).

## Redesigned desktop workflows

The six primary destinations are Overview, Connected Devices, Library, Backup Manager, Logs and Settings. Compatibility remains in device details. Overview contains only four current statistics and active jobs; historical work belongs in Logs. One shared provider reads saved jobs and drives real completion/failure notifications across navigation. Stage-specific byte progress is measured; unreliable percentages and ETAs are omitted.

Library supports global type and sort filters alongside existing search/integrity/source/date filters. User imports show Imported Original, never Extracted. Restored copies show Restored Default; future acquired/build/customized categories require corresponding recorded provenance. Details retain checksum, imports, integrity history and device association. Customize shows four unavailable feature switches; it cannot start a proprietary rebuild or a device write.

Create Backup streams and independently verifies a separate copy under the managed per-user `backups` directory. Backup Manager preserves the source and checksum. Confirmed Restore rechecks the backup before copying through the existing import pipeline, adds `_DEFAULT` before the extension and resolves case-insensitive conflicts with a suffix. The original backup remains intact. Latest 100 active backup records are shown.

Delete requires a file-specific confirmation and no active library work. It removes only that item's active catalog entry, retaining bytes, provenance, backups and job history for recovery. It does not free disk space or permanently purge data. Counts/byte summaries describe active catalog images, not all retained or orphaned disk files. Reimport or a verified backup restore recovers a removed Library image.

Additive schema 5 stores GUI preferences, backup metadata, presentation labels and removal timestamps; existing theme JSON and historical rows remain. Settings can request a native folder-selection copy plan. Only a reviewed opaque ticket can queue relocation. Registered blobs are copied and independently verified before the final transaction selects the future location. Imports pause until restart activates it, while the original directory remains. Failure/cancellation preserves the old location and uncertain outputs. Backup storage and the workspace database do not move.

See [GUI verification](GUI_REDESIGN_VERIFICATION.md) for actual native results and limitations.
