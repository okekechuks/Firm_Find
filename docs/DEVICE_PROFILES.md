# Device profiles

Phase 3 adds declarative JSON profiles to the existing Windows desktop app. The registry lives in `apps/desktop/src-tauri/src/profiles/mod.rs`; it loads an explicit bundle, validates each document independently, quarantines malformed or duplicate entries, and keeps IDs sorted for deterministic lookup. `Registry::by_id` supports an explicit active version. Arbitrary files are never discovered or executed as profiles.

`schemaVersion: 1` specifies the format. `profileVersion` is a separate numeric three-part content revision. No previous profile schema exists to migrate. Unsupported schemas are rejected safely. The review schema is `device-profiles/schema-v1.json`; Rust is the authoritative semantic validator. JSON must be at most 65,536 bytes, depth 16, 4,096 values, 64 entries per collection, 1,024 bytes per string and 64 bytes per key. IDs have a smaller 96-byte lowercase bound. Duplicate keys at every depth, unknown fields/enums, invalid dates, unresolved evidence references, missing sub-capabilities, reversed ranges and executable command fields are rejected. Numeric firmware releases use three components; opaque vendor versions remain observations, with unknown applicability.

Each profile records identity, aliases, exact hardware revisions, firmware families and constraints, match-rule purpose, declared management paths, modem information, four independent capabilities and their sub-capabilities, limitations, evidence sources, review date and provenance. Unknown values are explicit. A documented pathway does not mean its adapter exists. OBTAINER owns adapter availability and never accepts it from profile JSON.

The bundle contains two deliberately different records:

- `observed.comfi-mg11`: Phase 2 local USB/network observations and an owner-reported retail label. USB `1286:4E31` only suggests a candidate. No verified revision, firmware identity, chipset, modem model or feature support is claimed.
- `tplink.archer-c7-v5.openwrt-23-05-5`: a curated documentation reference, limited to Archer C7 v5, target `tplink,archer-c7-v5`, OpenWrt 23.05.5. DNS documentation describes upstream forwarding and LAN IPv4 advertisement separately. IPv6 and persistence applicability remain unknown. Wi-Fi AP hardware evidence does not establish client limits. APN/USSD remain unknown. This historical release is not an installation recommendation; the project has not physically qualified an Archer C7.

The second record draws on the official [OpenWrt hardware data](https://openwrt.org/toh/hwdata/tp-link/tp-link_archer_c7_v5), [23.05.5 image selector](https://firmware-selector.openwrt.org/?id=tplink_archer-c7-v5&target=ath79%2Fgeneric&version=23.05.5), [DNS configuration reference](https://openwrt.org/docs/guide-user/base-system/dhcp_configuration) and [DNS service description](https://openwrt.org/docs/guide-user/base-system/dhcp). These establish documented target/service behavior, not the runtime contents of a connected device. Local MG11 evidence references the existing Phase 2 report rather than an invented web source.

Trust is assigned by the application's explicit bundle manifest and source category, never by an imported claim. Experimental, observation and locally unverified records cannot grant authoritative support. The Compatibility page's local JSON validator returns a `local_unverified` preview; it does not install or activate a profile. Signed distribution and community updates are future work.

SQLite migration `003_profiles.sql` adds `profile_versions`, `compatibility_evaluations` and `device_identity_observations` in the existing database directory. Startup inserts missing profile versions without rewriting existing documents; changed content reusing the same ID/version is quarantined. Evaluation metadata stores engine/registry/input digests, profile version/hash, evidence and reasons, plus one bounded prior report per device. Re-evaluation explains changed inputs or registry versions; cached decisions never become identity evidence.

User reports are append-only, bounded to 32 observations per device and 256 bytes each, deduplicated by device/field/value. Rust fixes their origin to `user_supplied`, verification to `user_reported`, and reliability to `hint`. Users cannot submit trusted management identity or verification flags. `LT800/` remains an unclear reported identifier, not a confirmed revision or MG11 alias. The supplied `MF69_AM802L_ZX_DD_N_241106_EU` remains an opaque reported software version.
