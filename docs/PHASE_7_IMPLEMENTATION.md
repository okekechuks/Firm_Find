# Phase 7 implementation

Revision: 20 October 2026. This document describes the implemented source and its boundaries. Exact executed commands, exit codes, native screenshots and acceptance verdicts belong in [Phase 7 verification](PHASE_7_VERIFICATION.md). Phase 7 adds pinned SSH inspection of a selected OpenWrt endpoint to the existing desktop application. The six sidebar destinations, Windows discovery, profile registry, Phase 5 adapter framework, Phase 6 simulator, Library, Backups, Logs and Settings remain in their existing structure.

## Trust and approval lifecycle

1. **Select an existing saved endpoint.** The backend resolves its numeric local management IP and active physical Windows interface. Loopback is excluded from production target selection. Every connected host address is excluded, including an address belonging to another PC interface with overlapping prefixes. Names, USB IDs and gateway observations do not grant router identity.
2. **Approve one bounded host-key observation.** The request names the saved target and SSH port. The backend records a current target/evidence snapshot and observes one Ed25519 host key. The resulting fingerprint is explicitly untrusted.
3. **Independently verify the fingerprint.** The user supplies the matching SHA-256 fingerprint from a trusted independent source and approves one identity/authentication handshake. Copying the fingerprint from the same untrusted network response does not establish independent verification.
4. **Select an existing key natively.** The backend reserves its exclusive operation before opening Windows `GetOpenFileNameW`. No key content or key path crosses React/IPC. The modal has a bounded selection lifetime and cancellation hook. After selection, the IPC resolver refreshes saved target, interface and evidence before authentication.
5. **Authenticate and retrieve identity only.** `SshTarget` enforces the exact host pin and selected source address. The prepared adapter independently compares actual endpoint, fingerprint and source scope with the `SessionBinding`. Existing `HandshakeApproval` and `SessionManager::connect_initial()` authorize the single fixed board query. No preseeded authenticated identity or exact unknown firmware profile is required to begin this restricted handshake.
6. **Evaluate authenticated identity.** The existing profile engine evaluates the actual model, board/target/build and firmware release. A missing manufacturer or hardware revision stays unknown. Ambiguous/conflicting identity remains denied. An unmatched genuine OpenWrt identity can be shown as identity-only; it grants no configuration reads.
7. **Approve configuration inspection separately.** Only a unique exact trusted profile can obtain an established `ReadConfiguration` grant through `confirm_session_reads()`. Endpoint/interface/source pin, discovery/evidence/profile snapshots and expiry remain bound. The handshake receipt cannot authorize this step.
8. **Inspect once and validate publication.** Each SSH query checks the pin again. Board identity is compared before and after the configuration/metadata sequence. One approval grants one inspection; another run requires fresh read approval. Results are rejected if cancellation, identity, discovery, selected endpoint or evidence changed.
9. **Disconnect, cancel or expire.** Backend session/grant/observation resources are revoked and child processes are killed/reaped. Normal closure/navigation also requests cleanup; React suppresses late responses from older UI operations.

The exposed status states are `idle`, `host_observed`, `identity_only`, `read_authorized`, `inspected`, `disconnected` and `failed`. An acknowledged report may remain displayed after its one-use grant is consumed; the `inspected` state requires a new approval before another remote read.

## Closed query registry and minimization

`ReadQuery` has exactly eight variants. IPC accepts none of their command text and exposes no arbitrary-command variant.

| Variant | Constant operation and returned projection | Output bound |
| --- | --- | --- |
| `Board` | `/bin/ubus call system board`; model, board, release/build/target and optional rootfs type | 16 KiB |
| `Network` | Fixed ucode UCI projection of interface name/protocol, configured DNS/peer-DNS, APN, automatic-APN flag, `pdptype` and authentication method | 64 KiB |
| `RuntimeDns` | Fixed local ubus call to `network.interface`/`dump`, projected to name/up/protocol/`dns-server` before transmission | 64 KiB |
| `DhcpDns` | Fixed UCI projection of interface, DNS-specific IPv4 DHCP options and IPv6 DNS/advertisement fields | 64 KiB |
| `Wireless` | Fixed UCI BSS projection of name/radio/SSID/mode/disabled/configured `maxassoc` | 64 KiB |
| `WirelessRadios` | Fixed UCI radio projection of name/type/disabled/configured aggregate `maxassoc` | 64 KiB |
| `WirelessRuntime` | Bounded local hostapd-object enumeration, approved status/client methods, selected driver/PHY/status and associated-client count | 64 KiB |
| `Partitions` | `/bin/cat /proc/mtd`; identifiers, names, sizes and erase sizes only | 16 KiB |

The router performs field selection before transmission. Wi-Fi keys, credentials, SIM PINs, private keys, arbitrary protocol `data` and client MAC records are excluded. Strict parsers bound collection counts and strings, reject duplicate sections, validate addresses and reject unknown configuration fields. Successful malformed/oversized output fails closed. An unavailable optional metadata interface yields an explicit limitation and unknown result; it does not fabricate support.

Configured DNS, runtime-reported DNS and LAN advertisement settings have separate fields. None proves resolver reachability or what a client received. BSS and radio limits are separate stored settings; neither proves driver capacity/enforcement. APN/protocol observations do not prove a present supported modem. USSD remains passive and unknown without qualified interface evidence. Exact official-source mappings and limitations are recorded in [OpenWrt research](PHASE_7_OPENWRT_RESEARCH.md).

## Reuse of Phase 5 and compatibility

The production registry extends the existing `openwrt-readonly-contract` entry instead of introducing a duplicate adapter or identity engine. Its implementation is `BuiltIn`, version `0.2.0`, with SSH-key authentication and identity/capability/configuration-read operations. The default descriptor has no prepared endpoint and cannot connect until the backend supplies the single-use pinned target.

`HandshakeApproval`, `SessionBinding`, `EndpointTrust`, `Secret`, `OperationControl`, typed `AdapterError`, `SessionManager`, profile evaluation and established authorization are reused. Unknown OpenWrt identity gets a narrowly restricted bootstrap; it never skips the established read gate. Simulator authority cannot construct a physical grant, and simulation IPC has no route to this adapter.

Schema version 1 retains its exact hardware-identity requirements and serialized content hashes. Version 2 requires explicit `inspectionOnly: true`, one exact firmware release, an exact management identity containing board/target/build, and OpenWrt family. It cannot invent manufacturer or hardware revision. All four feature assessments and their subcapabilities must remain `UNKNOWN`; no verified range is permitted. Such a profile authorizes qualified OS inspection only, with explicit policy denial of backup/transaction/build/write authority. Imported or weak profile hints retain their existing non-authoritative behavior.

## Concurrency and stale-authority corrections

- An RAII guard atomically acquires the single operation slot. Only its token owner releases busy state. Each admitted operation has a distinct generation; publication checks token ownership and generation while holding the publication lock.
- Cancel signals the existing owner and waits a bounded interval. It cannot clear a later owner's token or busy state; contention/remaining cleanup is explicit. Idle and repeated cancellation remain scoped operations.
- Failed owned operations clear consumed host observations, dead sessions, grants and old reports. A late failure from an older generation cannot erase a newer operation.
- Discovery revisions notify this service's private session authority, cancel in-flight work and invalidate pending observations/read grants. IPC also re-resolves current selected state before acknowledging successful results.
- Established reads use the earliest session, grant and evidence expiry, capped by the caller's monotonic deadline. The same bounded control covers all remote queries, and authorization is checked again before successful session/result publication.
- The key picker holds admission ownership, has cancellation/timeout handling, and refreshes the backend-selected target immediately before authentication.

## Transport dependencies and credentials

The current qualified Windows transport path is Git for Windows OpenSSH: `C:\Program Files\Git\usr\bin\ssh.exe`, plus sibling `ssh-keyscan.exe` and `ssh-keygen.exe`. Investigation selected version 10.2 after Windows OpenSSH 9.5 keyscan could not negotiate the guest's key exchange. Missing/unsupported tools fail explicitly; no algorithm downgrade is added. No new Rust/npm dependency is needed for this external-client route.

Commands are invoked directly with separate arguments, an isolated public-key known-hosts file and strict checking. User SSH configuration, agents, passwords, interactive authentication, forwarding, proxies and connection sharing are disabled. Both output pipes are drained with bounds; raw peer diagnostics are classified into safe typed errors rather than logged verbatim. Cancellation, deadline and failure paths kill and reap the child. Temporary trust directories contain public host keys only and remove only their own created entries.

Private keys remain existing user-owned files selected through Windows. Password authentication, interactive encrypted-key prompts, credential persistence, new router users/keys and package installation are outside this implementation. A privileged SSH account may itself write; OBTAINER limits its own dispatch to the reviewed inspection allowlist.

## Firmware reports and storage

The feasibility model includes acquisition, physical extraction, partition layout, image format, build, installation, recovery and separate direct-configuration/firmware-rebuild pathways for all four features. Every assessment has `executable: false`. Only the researched exact release/target yields a constant official-source/ImageBuilder candidate, with remaining compatibility/authenticity/tool requirements.

These reports are session metadata and serialized verification evidence, not firmware bytes, backups, generated images or enabled operations. No firmware artifact is invented, existing vault items are not overwritten, and no application-data relocation or database migration is required by this inspection layer. See [firmware feasibility](PHASE_7_FIRMWARE_FEASIBILITY.md) and the proposed [firmware pipeline milestones](FIRMWARE_PIPELINE_ROADMAP.md).

## Controlled test entry point and current production limit

The genuine interoperability target is OpenWrt 25.12.6 x86/64, revision `r33311-981c978eff`, booted from the recorded official image in an owned disposable QEMU guest. `scripts/openwrt-test-vm.py` manages only that marked guest and its generated test key/temporary guest setup. WSL/QEMU is a test-fixture dependency, not a requirement for ordinary desktop startup.

The native-test binary requires its existing marked isolated profile plus explicit `--openwrt-lab`. The loopback target is sealed to `127.0.0.1:22270` and an exact inspection-only OS profile. Its provenance states virtual OS interoperability, not physical hardware testing; manufacturer/revision and all four hardware feature capabilities remain unknown. The added profile is sorted before registry lookup and remains confined to that native-test process. Ordinary production entry points reject lab activation and do not install that profile in normal SQLite storage.

The ordinary production adapter can perform a separately approved pinned identity-only handshake with an eligible selected endpoint. **There is currently no physically qualified production target/profile that passes the configuration-read gate.** The existing hardware reference profile needs exact independently qualified manufacturer/revision evidence, which this board-only adapter does not invent. The native-only QEMU profile does not broaden production hardware support. The owner's regular proprietary MiFi remains unsupported for these OpenWrt operations; [physical qualification is PENDING](PHASE_7_HARDWARE_QUALIFICATION.md).

## Verification surfaces

Rust tests reside beside transport/query/runtime/feasibility code and in the retained adapter/profile test modules. Genuine-guest tests are explicitly ignored by default and must be invoked against the owned guest; fixture tests alone cannot establish protocol interoperability. Frontend tests use explicit synthetic IPC fixtures. `scripts/verify-openwrt.mjs` extends the existing native verifier, and `npm.cmd run test:openwrt` invokes the retained GUI/library/adapter/simulator checks plus Phase 7.

The authoritative [verification report](PHASE_7_VERIFICATION.md) must record what actually ran, initial failures/corrections, both executable builds, native development/production behavior, screenshots, normal-data preservation and separate software/hardware verdicts. This implementation document does not predeclare those results. Phase 8 simulator work may proceed only according to the accepted software gate; physical firmware/configuration operations remain at their dedicated future qualification gates.
