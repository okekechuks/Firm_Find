# Application architecture

This document describes existing code. The [master plan](../RFS_MASTER_PLAN.md) defines the proposed structure and configuration-first direction; planned modules are not implemented merely because they appear there.

Tauri 2 hosts locally bundled React/TypeScript in Windows WebView2. Tailwind's Vite integration provides styling support; local CSS defines the visual system. Rust owns all application persistence. A single Cargo workspace member keeps the foundation small; domain and repository modules provide extension points without premature service boundaries.

The command inventory is maintained in `apps/desktop/src-tauri/build.rs`, registered in `src/lib.rs`, and granted through `capabilities/main.json` and the isolated-only `capabilities/simulator.json`. It covers workspace/settings, Windows discovery, explicitly approved endpoint checks, device profiles, jobs/firmware Library/backups, storage recovery, simulator operations and pinned OpenWrt inspection. TypeScript validates responses at the boundary. See [the adapter implementation](PHASE_5_IMPLEMENTATION.md), [simulator architecture](SIMULATOR_ARCHITECTURE.md) and [OpenWrt implementation](PHASE_7_IMPLEMENTATION.md).

Repository requests run in Tauri's blocking worker pool and share a mutex-protected SQLite connection. Database initialization enables foreign keys, WAL, a busy timeout, and an atomic schema migration. A newer schema is rejected. A per-user workspace mutex is acquired before opening data. Fatal ordinary-release startup errors appear in a native Windows dialog. An unavailable relocated Library permits metadata/settings access and an explicit confirmed default-location recovery; previous bytes and records are retained.

Theme selection persists in SQLite. Browser preview has no database, exposes no simulated success and permits only temporary theme preview. Hash navigation supports history and direct screen links. System theme tracks the operating system preference.

Daily JSON logs go to the generated application data folder. The nonblocking writer guard is retained for the application lifetime. Credentials and raw hardware identifiers are not written to logs or audit records. Local Device Explorer may display raw Windows identifiers; its inventory database keys use stable SHA-256 digests.

Device counts come from reconciled Windows inventory; Library and job counters come from persisted records. A dedicated Rust worker reads SetupAPI/Configuration Manager and IP Helper snapshots. Plug-and-play and IP-interface callbacks enqueue bounded signals. The worker coalesces changes and rescans every 30 seconds when automatic refresh is enabled. Unchanged, cancelled and failed scans retain the authorization revision; only a committed inventory/evidence change advances it. Failed/cancelled scans do not refresh evidence age. Database records use hashed identifiers; audit records exclude raw identifiers. Firmware files are copied and independently hashed by the bounded Library worker, without executing or unpacking them.

The revised roadmap starts with supported configuration interfaces and a simulator, followed by shared transactions and DNS, Wi-Fi client-limit, APN, and USSD workflows. USSD administration must run on the router. Supported OpenWrt image builds and conservative OEM feasibility follow later. Configuration writes require exact profile evidence, preview, preflight, a verified before-state, explicit consent, verification, and rollback or recovery. Firmware installation is outside the revised phases 0–19.

The application command manifest opts into Tauri ACL enforcement. Only the local `main` window receives the explicitly granted application commands and event listen/unlisten operations. Simulator IPC is granted only by the dedicated isolated configuration and also checks backend provenance. There is no general shell, filesystem, network or SQL plugin permission. OpenWrt uses fixed commands through pinned, bounded OpenSSH: one identity login followed, if separately approved and qualified, by one framed inspection login. No caller-supplied command is accepted. Fingerprint review, authentication and established reads have separate expiry limits.
