# Persistent library jobs

The existing SQLite `jobs` table remains authoritative, including its original status constraint. Schema 4 adds `job_details`, preserving every legacy ID/status. New jobs are `firmware_import` and `integrity_verify`; there are no router acquisition/configuration/flashing jobs. Metadata export is bounded off-UI work with a persisted activity event, not an unbounded worker job.

Legal transitions are pending → running/cancelled/failed and running → completed/cancelled/failed. Terminal jobs cannot return to running; cancellation of a terminal job is an idempotent read. Interrupted jobs use `failed` with error code `INTERRUPTED`, preserving compatibility with the original status constraint. Unknown legacy job kinds remain historical records and cannot be cancelled by the new service.

One named worker drains a bounded channel. At most 16 jobs, including active work, can be accepted. The service does not create a thread per binary import. File I/O/hashing occurs outside the SQLite mutex; metadata transactions and progress writes are short. The current filename, optional description and device association are saved as intent before file copying; source absolute paths and selection handles are not persisted.

Progress records contain durable job ID/kind/status, stage, real bytes/total, timestamps, cancellation state, artifact/import relationships, duplicate result and structured sanitized errors. Byte counts describe the current stage. Notifications (`library-job-changed`) are throttled at approximately 100 ms for data processing, with immediate stage/terminal updates. React validates notifications, throttles reads and refetches persisted records; 1.5-second polling also handles missed notifications. Events are hints, not the source of truth.

Cancellation uses an atomic flag checked between chunks and state transitions. A finalization mutex orders cancellation against successful metadata commit. The response may be `completed` if completion already won the fence; the UI must report the persisted result. Accepted cancellation never marks partial data successful. Near-publication cancellation preserves any complete orphan blob rather than risking deletion of shared content. Cancelling duplicate verification does not label previously valid content corrupt.

Successful import commits artifact metadata, occurrence/provenance, integrity history, job completion and activity together. Verification saves its actual result/history before the terminal job status. Audit events remain in `audit_events`; `activity_links` adds job/artifact/severity relationships instead of duplicating event text in a competing activity system. Progress does not spam the audit trail.

Startup fails unfinished owned jobs, cleans only known regular staging paths, retains diagnosable published bytes and reconciles stored artifact availability/size. Graceful shutdown stops new work, requests cancellation, releases tickets and waits at most two seconds for the worker. Forced process termination relies on startup recovery. A blocked OS read can exceed that graceful interval; the next launch recovers the durable pending/running state.

Errors use stable codes such as `FILE_MISSING`, `ACCESS_DENIED`, `FILE_TOO_LARGE`, `DISK_FULL`, `UNSAFE_PATH`, `SOURCE_CHANGED`, `HASH_MISMATCH`, `DATABASE_UNAVAILABLE`, `INTERRUPTED`, `CANCELLED`, `QUEUE_FULL` and `ATOMIC_PUBLICATION_UNAVAILABLE`. UI messages omit internal paths and panic traces. Recovery requires reselecting the original source; interrupted work is not silently resumed or reported successful.
